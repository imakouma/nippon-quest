# Spec: AI 前提の Question Playground 再設計

2026-10-30。状態：A「レビュー・ワークスペース」承認済み・実装中。

## Objective

Question Playground を、問題コードを直接編集しない人が AI と一緒に教材を改善するための確認画面へ再設計する。

主な操作順を「問題を探す → 内容を読む → 実際に解く → 結果を確認する」とし、JSON、内部 ID、登録タイプ、`QuestionResult` などの技術情報は通常操作から退避する。既存の問題選択、検索、フォルダ、実行、採点、直リンク、再読込、エラー確認は維持する。

今回の変更は AI モデルやチャット機能を新設しない。既存の Web エディタは AI 編集機能ではないため、AI 機能のような名称には変更しない。

## Users and Primary Workflow

- 主利用者：問題コードを直接書かず、AI に修正を依頼し、ブラウザ上で結果を確認する開発者・教材担当者。
- 副利用者：問題レンダラーやデータ不備を調査する開発者。
- 主動線：フォルダまたは検索で問題を選ぶ → プレビューで解く → 人間向けの結果を確認する → 必要なら共有 URL または Web エディタへ進む。
- 副動線：技術情報を開き、元ファイル、問題 ID、JSON、スキーマエラー、結果 JSON を確認する。

## Research Summary

### Current-page findings

- 左側の先頭に英語タイトル、内部ファイル、問題 ID、JSON が並び、利用者の目的より実装詳細が強い。
- プレビューは大きいが、空の黒い領域として見え、問題選択との関係が分かりにくい。
- 「表示」「中断」「登録タイプ」「QuestionResult」が同じ強さで並び、主要操作が判別しづらい。
- フォルダツリーは有効だが、画面下部に離れているため「探す」と「確認する」の往復距離が長い。
- 表は監査には有効だが、8列の情報量が多く、通常の問題選択には重い。
- 320px では既存機能は利用できるが、デスクトップ構造を縦積みにしただけで優先順位が整理されていない。

### Reference lock

- ユーザー提供の現行画面を、保持すべき機能と改善前の比較基準にする。
- Refero の bundled craft references を基準にし、作業用 UI として中立色、明確な階層、少ない面数、読みやすい密度を採用する。
- 装飾的なグラデーション、紫中心の「AIらしい」配色、カードの過剰な入れ子、ダッシュボード風の不要な指標は採用しない。
- ライブ Refero 調査は使用しない。外部デザインの複製や新規画像素材も行わない。

## Visual Directions

### A. レビュー・ワークスペース（推奨）

```text
┌ ヘッダー：問題レビュー / ゲームへ / Webエディタ ─────────────┐
│ ┌ 探す ─────────┐ ┌ プレビュー ─────────────────────┐ │
│ │ 検索・絞り込み  │ │ 選択問題の名前・教科・学年         │ │
│ │ フォルダツリー  │ │ 960×540の問題ステージ             │ │
│ │ 問題の短い一覧  │ │ [もう一度試す] [中断]             │ │
│ └──────────────┘ ├ 結果：正答/時間/回数を文章で表示 ───┤ │
│                   │ ▸ 技術情報（ID・JSON・結果JSON）    │ │
│                   └──────────────────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

- 探索と確認を常に隣接させ、現在選択中の問題を見失いにくい。
- 既存コンポーネントの並べ替えと CSS 改修が中心で、最小の変更で目的を満たせる。
- 問題数が多くてもツリー、検索、一覧を一つのナビゲーション領域として扱える。

### B. 教材カタログ

```text
┌ ヘッダー ───────────────────────────────────────────────┐
│ フォルダ / 検索 / 絞り込み                               │
├ 問題カード一覧 ─────────────────────────────────────────┤
│ 問題文・教科・学年・選択肢・状態をカードで閲覧            │
└ 選択時に右側ドロワー：プレビュー / 結果 / 技術情報 ───────┘
```

- 問題内容の見比べを最優先にできる。
- 既存の表をカードへ大きく作り替えるため、変更量と回帰範囲が増える。
- 大量データでは画面密度が下がり、監査用途には不利。

### C. 検証ワークベンチ

```text
┌ ヘッダー / テスト条件 / 実行 ────────────────────────────┐
│ ┌ プレビュー（主役）──────────────┐ ┌ 選択問題の詳細 ──┐ │
│ │ 960×540 ステージ                │ │ 問題文・答え     │ │
│ └───────────────────────────────┘ │ 結果・エラー     │ │
├ 下段：フォルダ / 問題表 / 技術情報 ───────────────────────┤
```

- レンダラー開発と反復テストには最も向く。
- 「問題を探す」領域が下段に残り、AIで教材を編集する人の主動線には開発者寄りすぎる。

## Recommended Direction

A「レビュー・ワークスペース」を推奨する。ユーザーの主目的に最も近く、既存のデータ読込・問題実行・一覧ロジックを維持したまま、情報の優先順位とレイアウトを改善できるため。

## Technical Scope

### Likely files

- `playground.html`：既存 inline style を整理し、ページ全体の基礎だけを残す。
- `src/tools/playground.tsx`：ヘッダー、問題概要、テスト操作、人間向け結果、折りたたみ技術情報へ再構成する。
- `src/tools/playground.css`：デスクトップ、タブレット、モバイルのレイアウトと状態表現を実装する。
- `src/tools/QuestionList.tsx`：探索領域に合う情報量とラベルへ整理する。
- `src/tools/QuestionTree.tsx`：既存カタログ契約を維持し、選択状態と件数を読みやすくする。
- `content/i18n/ja.json`：新しい利用者向けラベルを追加する。
- `tests/e2e/playground-list.spec.ts`：主要動線、技術情報、レスポンシブ、キーボード操作を固定する。
- `docs/01_ARCHITECTURE.md`：Playground の主動線と技術情報の位置づけを更新する。

### Existing behavior to preserve

- `?q=<問題 id>` の直リンクと URL 更新。
- 4,829 問の全件読込、8並列上限、先頭200問表示。
- 教科・学年・タイプ・単元・文字検索、サンプル、エラーだけの絞り込み。
- カタログがない旧 manifest のフォールバック。
- フォルダの教科 → 学年 → 単元 → セット構造。
- 学年による漢字表示、制限時間、問題実行、中断、再読込。
- 無効な JSON、未登録タイプ、payload、不正問題のエラー表示。
- 元 JSON の確認と必要時の手動実行。通常は閉じた「技術情報」内へ移す。

### Developer-only entry points

- 公開用の本番ビルドには `playground.html` と `editor.html` を含めない。
- ローカル開発用ビルドだけが両ページを生成する。
- ゲームの開発者モードを ON にしたときだけ、メニューへ「問題一覧」「問題編集」を表示する。
- 公開ホストでは `?dev` を付けても開発者モードを有効にしない。
- ローカルであっても開発者モードが OFF の間は、ゲーム内メニューへ開発ツールを表示しない。

## Interaction Requirements

- 問題未選択時は、黒い空画面だけでなく「左から問題を選ぶ」空状態を表示する。
- 問題選択時は問題文または単元名、教科、学年、タイプをプレビュー上部に表示する。内部 ID は副情報にする。
- 主要ボタンは「この問題を試す」または「もう一度試す」とし、実行中のみ「中断」を有効にする。
- 結果は、正答度、所要時間、回答回数、時間切れの有無を人間向けに要約する。生の `QuestionResult` は技術情報に残す。
- JSON は初期状態で閉じる。既存の編集・再実行能力は保持するが、直接編集を推奨する文言は使わない。
- エラーは問題選択やテスト操作の近くに表示し、技術的な詳細も失わない。
- Web エディタへの導線は現在の機能に合わせて「Webエディタ」と表記し、AI 編集機能とは表現しない。

## Visual System

- 背景：温かみのある薄いグレー。主要面は白。プレビューはレンダラーの黒背景を維持する。
- 主要色：落ち着いた青緑または濃紺を一色だけ使用し、選択・フォーカス・主操作へ限定する。
- 状態色：成功は緑、注意は琥珀、エラーは赤。色だけに依存せず、アイコンと文言を併記する。
- 書体：操作 UI は system sans、ID・JSON・ファイルパスだけ monospace。
- 面：ヘッダー、探索、プレビューの3領域を明確にし、各小要素をカード化しない。
- 余白：8px 系列。本文14〜16px、補助12〜13px。操作対象は原則44px以上。
- アニメーション：状態変化の短い transition のみ。装飾的な動きは追加しない。

## Responsive and Accessibility

- 1440px以上：探索 320〜380px、右側にプレビューと結果。
- 768〜1439px：探索 280〜320px、プレビューは残り幅。表は領域内スクロール。
- 767px以下：ヘッダー → 選択問題 → プレビュー → 操作・結果 → 探索 → 技術情報の順に縦積み。
- 320pxでページ全体に横スクロールを発生させず、問題表だけを必要に応じて横スクロール可能にする。
- すべての入力に可視ラベル、すべての操作にキーボードフォーカスを持たせる。
- `focus-visible`、十分な色コントラスト、状態文言、空状態、読込中、エラー状態を用意する。
- `details/summary`、`button`、`select` など既存のネイティブ要素を優先する。

## Testing Strategy

- E2E RED：新しい主要ランドマーク、問題選択→実行→要約結果、技術情報の初期閉鎖、320/768/1440px、キーボード操作を先に固定する。
- GREEN：既存ロジックを移動し、必要最小限の表示変換だけ追加する。
- 回帰：全件数、8並列、フォルダ選択、旧 manifest、直リンク、検索、JSON確認を維持する。
- 実ブラウザ：通常問題、エラー問題、未選択、実行中、完了、時間切れを確認する。
- 完了ゲート：`pnpm lint`、`pnpm check:architecture`、`pnpm test`、`pnpm validate:content`、`pnpm build`。

## Boundaries

### Always

- 既存の `QuestionBase`、`QuestionRenderer`、`QuestionResult` 契約を変更しない。
- `questionCatalog` を階層の正として使う。
- 新規依存を追加せず、Preact、CSS、ブラウザ標準要素を使う。
- AIが編集する前提を情報設計へ反映するが、存在しないAI機能を表示しない。
- 既存の問題データ、学術レビュー、セーブデータを変更しない。

### Ask first

- Playground 内へのAIチャット、モデルAPI、認証、外部サービス接続の追加。
- Webエディタ自体の機能変更。
- `src/questions/contracts.ts`、schema、manifest 形式の変更。
- 問題内容や正答の変更。

### Never

- JSONや結果の技術情報を完全に削除しない。
- 表示のために問題タイプごとの分岐を Playground の一覧へ追加しない。
- デスクトップ専用の固定幅へしない。
- 現行の直リンクや共有可能な URL を壊さない。

## Success Criteria

1. 初見で「問題を探す」「問題を試す」「結果を見る」の3操作が判別できる。
2. JSON、ファイルパス、内部 ID、登録タイプ、結果 JSON が通常画面の主役ではない。
3. 問題を選ぶとプレビューと URL が更新され、そのまま解答・再実行できる。
4. 結果が生 JSON を読まなくても理解でき、必要時は生 JSON も確認できる。
5. 4,829問のフォルダ、検索、絞り込み、エラー監査能力を維持する。
6. 320、768、1024、1440px で主要操作が利用でき、ページ全体が横にはみ出さない。
7. キーボードだけで問題選択、実行、技術情報の開閉、一覧復帰ができる。
8. 既存 E2E と追加 E2E、標準ゲート、実ブラウザ確認が成功する。
9. 本番ビルドに問題一覧・編集ページが出力されず、ローカル開発者モードのメニューからだけ両ページを開ける。
10. 専用ブランチに原子的コミットとしてまとまり、統合前にユーザーが確認できる。
