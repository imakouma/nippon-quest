Status: implemented / 2026-11-25 Google専用へ変更。Googleの登録・秘密鍵設定・ログイン開始確認済み。本人ログイン後のcallback検証は未完了。

作成日: 2026-11-24 (Asia/Tokyo)

2026-11-25: ユーザー指示によりGoogleのみへ変更。アカウント画面・ゲスト保存・クラウド同期は維持する。

## 目的

Google でログインし、NIHON QUEST のゲーム進行と学習記録をアカウントに保存して、別の端末から続きを遊べるようにする。認証と保存は、この一つの利用フローとして検証する。

## 現行仕様と変更点

- 現行仕様: `docs/00_GAME_DESIGN.md` §8、`docs/01_ARCHITECTURE.md` §1。「ログイン不要、個人情報を取らない」、端末内保存のみ。
- 今回の依頼に合わせ、任意のアカウント保存を追加する。ログインせず遊べる機能は維持する。
- `src/core/state/save.ts` が IndexedDB の保存・復元・バックアップを集約している。
- 既存の 3 スロット、GameState、旧形式の migration、JSON エクスポート／インポートを引き継ぐ。
- 同期対象は各スロットの GameState（進行、仲間、所持品、図鑑、学習記録、ゲーム内設定）。端末固有の開発設定・認証情報は含めない。
- 保護者がアカウントを管理する想定。子どもの実名・住所・電話番号・誕生日の入力欄は作らない。認証用識別子と学習データを扱うことはログイン前に説明する。

## 利用フロー

1. タイトルの「アカウント」から Google ログインを選ぶ。ログインは必須にしない。
2. 初回は、この端末のどの冒険をアカウントへ引き継ぐか、スロットの名前・進行・更新日時を見て選ぶ。無断で全データをアップロードしない。
3. ログイン済みの冒険は、通常のセーブ時に端末へ保存後、クラウドへ同期する。未同期・同期中・同期済み・再試行待ちを表示する。
4. 別端末では同じログイン方法で入り、クラウドのスロットを選んで再開する。
5. 初回引き継ぎや複数端末で同じスロットが変更された場合は、双方の進行を表示して選択する。選択前はどちらも消さず、更新日時だけで自動上書きしない。
6. 通信断でも端末への保存は続ける。再接続後、元のアカウントの認証を確認して再送する。
7. ログアウト時は同期を停止し、プレイ中データと画面を切り替えてゲストのタイトルへ戻る。別アカウントの画面へ前の人のデータを出さない。
8. アカウントのクラウドデータのエクスポートと削除を可能にする。削除とログアウトは別操作にする。

## データ保護と境界

- ローカルの保存領域・バックアップ・送信待ちキューをゲスト／アカウントごとに分離する。既存ゲストデータは元の形式で読み、引き継ぎ成功までは保持する。
- データの所有者はサーバーで検証済みのセッションから取得する。クライアント指定の userId を信用しない。
- クラウドの一意キーはアカウント ID とスロット番号。更新はサーバー発行の revision を使う compare-and-swap とし、競合は 409 で返す。
- 削除も revision を伴う操作とし、古いオフライン端末から削除済みデータが復活しないようにする。削除競合は明示的に解決する。
- アカウント変更時に古い通信の結果を適用しない。送信待ちデータの所有者を途中で付け替えない。
- API で GameState とサイズ上限を検証する。未知の将来バージョンは拒否して元データを残す。
- HttpOnly／Secure／SameSite Cookie のセッション、許可済み origin、OAuth state・nonce・対応する PKCE 検証、期限切れ処理を使う。認証用乱数は暗号学的乱数とし、ゲーム用 RNG は使わない。
- OAuth secret、DB 接続文字列、トークンはブラウザ配信物・Git・ログに入れない。
- OAuth／保存 API のレート制限を設ける。多重インスタンスでは共有 DB 等で制限する。
- ローカル開発の `resetSaves` はクラウド削除へ波及させない。
- アカウント削除時はセッションを失効し、所有するセーブ・認証連携を削除する。運用バックアップの保持期間と削除後の復元時の扱いを公開前に確定する。

## 技術方針案

- Phaser・Preact・Vite と既存の端末保存を継続する。
- 認証候補は Better Auth、永続 DB は PostgreSQL、サーバーは Node.js。Google の公式プロバイダー実装があり、Preact からフレームワーク非依存のクライアントを利用できるため。
- ゲームと API を同一 origin で配信する構成を優先する。現行の静的配信だけでは Cookie 認証とクラウド保存 API は動かないため、公開先の設定が必要。
- 追加依存候補は `better-auth` と `pg`（および必要な型定義）。採用時に固定バージョン・Node 要件・脆弱性・依存スクリプトを確認する。
- クラウドサービスの契約や公開先は未確定。料金の発生を伴う契約・本番環境への資格情報追加は、具体的な構成を示して確認する。
- 同じブラウザの同一アカウントは Web Locks で単一タブに制限する。再試行は認証完了と所有者一致を待ち、Service Worker は API をキャッシュしない。
- 本機能に AI モデルは不要。OmniRoute や外部 LLM にゲームデータを送信しない。

## 受け入れ条件と検証

- Google の実アカウントでログイン・キャンセル・ログアウトが動き、ログイン後の再読み込みでアカウントを維持する。
- 初回引き継ぎ後、別のブラウザ環境から同じ進行と学習記録を復元できる。
- 通信失敗、期限切れ、2 台同時更新、削除後の古い端末からの再送でデータが無断消失しない。
- A の通信中に B へ切り替えても、A のデータが B に表示・送信されない。他ユーザーの ID やスロットを指定しても読み書きできない。
- 既存ゲスト保存、バックアップ復元、JSON 入出力、3 スロット、通常のゲーム進行が回帰しない。
- 未設定の認証プロバイダーは成功したように見せず、利用できない旨を表示する。
- キーボード・タッチで操作でき、ふりがな、48px 以上の主要ボタン、ダイアログのフォーカス管理を守る。
